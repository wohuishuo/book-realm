# Spring AI 与 RAG

> **结论先行**:Spring AI 负责把 Java 后端接到大模型,RAG 负责让回答先找原文再生成。书域的 AI 服务不是凭空聊天,而是围绕书籍段落做有引用的阅读问答。

## 一句话

Spring AI = Java 调大模型的统一接口;RAG = 检索增强生成。

| 项 | 值 |
| --- | --- |
| 定位 | AI 服务开发框架 + 问答模式 |
| 模型接口 | OpenAI 兼容接口,可接 DeepSeek |
| 书域位置 | MVP-4 AI 服务 |
| 当前状态 | 摘要、embed、RAG 原文问答已跑通 |

## 解决什么问题

直接把一本书全文塞给大模型不现实:上下文太长、成本高、还容易胡说。RAG 的办法是:

1. 把书按段落切好;
2. 段落向量化;
3. 用户提问时先检索相关段落;
4. 把检索到的原文交给模型回答;
5. 回答里带引用。

```
用户问题
  │
向量检索相关段落
  │
把段落 + 问题交给模型
  │
生成带原文依据的回答
```

## 依赖关系

```
MVP-1 书库服务  → 提供书/章/段
        │
MVP-4 AI 服务   → 段落向量化 + 检索 + 调 LLM
        │
DeepSeek/OpenAI 兼容 API
```

AI 服务依赖书库的段落结构。MVP-1 把 Paragraph 单独成表,就是在为这里铺路。

## 在书域里的角色

MVP-4 目标不是"接一个聊天框",而是做阅读场景:

- 章节摘要;
- 划词解释;
- 围绕当前书籍问答;
- 回答引用原文段落。

## 真实踩坑

AI 服务要允许"没有 key 也能启动"。否则团队成员没有 `DEEPSEEK_API_KEY` 时,连健康检查和检索链路都跑不起来。当前实现会在 health 中报告 key 是否配置;没有 key 时返回本地降级结果和检索引用,有 key 时调用 DeepSeek 生成回答。
