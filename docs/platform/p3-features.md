# P3 功能分解树

> **结论先行**:书域平台 = 5 个独立 MVP 的功能合集,每个 MVP 独立可运行。砍单顺序为 MVP-5 书友匹配 → MVP-4 AI 摘要 → MVP-3 阅读进度事件 → MVP-2 书城搜索。

## 功能树

```
书域平台(电子书 + AI 问答)
│
├─ MVP-0 用户中心(认证服务)
│   ├─ 注册(用户名/密码)
│   ├─ 登录(返回 JWT)
│   ├─ Token 校验(拦截器)
│   └─ 发布 UserLogin 事件
│   【边界】只做认证,复用已完成的 user-center 仓
│
├─ MVP-1 书库服务(内容 API)
│   ├─ 书籍管理(CRUD + 封面文件)
│   ├─ 章节管理(目录 + 段落内容)
│   ├─ 搜索(按书名/作者,按标签过滤)
│   └─ 种子数据(公版书预置)
│   【边界】只提供 REST API,不包含前端页面和推荐算法
│
├─ MVP-2 阅读 App(Android Compose)
│   ├─ 登录(对接用户中心 JWT → DataStore)
│   ├─ 书架(收藏 + 最近阅读卡片 + Room 缓存)
│   ├─ 书城(书籍列表/搜索 + 详情)
│   ├─ 阅读器(分页渲染 + 进度记忆 + 字号 + 划词 AI 问答)
│   └─ 导航骨架(Hilt + Navigation)
│   【边界】只做阅读客户端,不内置书评/社交/书单
│
├─ MVP-3 事件驱动统计(RabbitMQ + 两微服务)
│   ├─ RabbitMQ 队列(exchange: bookrealm.events)
│   ├─ 日志服务(消费 UserLogin → 落盘)
│   ├─ 统计服务(消费 UserLogin + ReadingProgress → 聚合)
│   └─ 统计查询 API
│   【边界】只做事件消费与统计,不做实时看板
│
├─ MVP-4 AI 服务(Spring AI + RAG)
│   ├─ 书籍向量化(分段 → Embedding → 向量库)
│   ├─ RAG 读书问答(划词 → 检索 → LLM 回答)
│   └─ 章节摘要
│   【边界】只做文本理解,不做续写/角色扮演/推荐
│
└─ MVP-5 书友匹配(可选)
    ├─ 标签匹配
    └─ Redis 缓存
    【边界】MVP 阶段不启动,仅设计占位
```

**根据**:每个 MVP 的叶子节点能从 plan.md 的里程碑 DoD 中找到对应。如"阅读器/进度记忆"对应第 3 周 DoD"退出重进回到原位",划词 AI 问答对应第 4 周 DoD"阅读器内可弹出问答面板"。边界写清做什么不做什么——如书库不做前端页面,AI 不做角色扮演——防止范围膨胀。

**例子**:如果开发到第 3 周有人说"书架能不能做书单分享",回答是:看边界——书单属于社交,不在 MVP-2 边界内。这行边界就是砍需求的依据。

## 砍单顺序

**结论:砍单按依赖和重要程度排序,每砍一个平台仍完整。**

| 序号 | 砍掉 | 触发条件 | 后果 |
| --- | --- | --- | --- |
| 1 | MVP-5 | P 阶段后搁置 | 无影响 |
| 2 | MVP-4 摘要(留 RAG) | 第 4 周 AI 滞后 | RAG 问答仍是亮点 |
| 3 | MVP-3 阅读进度(留登录) | 第 4 周统计滞后 | 登录事件已满足训练课题 |
| 4 | MVP-2 书城搜索(留书架+阅读器) | 第 3 周 App 滞后 | 靠最近阅读和书名直达 |

**底线(不可砍)**:用户中心 + 书库 API + App 书架与阅读器 + 登录事件。缺任一样平台不完整。

**例子**:第 4 周结束时阅读进度事件没跑通→砍掉它,但登录事件还在——训练课题要求的"Login→fanout→日志+统计"闭环完整,可以单独交这份作业。书城搜索没做→砍掉它,但"最近阅读"卡片依然能跳转,不耽误核心阅读流。
