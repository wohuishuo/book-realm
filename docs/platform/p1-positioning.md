# P1 业务定位

> **结论先行**:业务领域、开发目标、用户画像——这个平台为谁解决什么问题。

## 一句话结论

**书域是一个以 RAG 读书问答为特色的开源电子书平台,让读者在"发现书、读进去、问得出来"这条链路上不走散。**

## 一、业务领域

**书域属于数字阅读 + 移动互联内容平台,核心是"读书 + 问答"——把电子书的阅读体验和 AI 驱动的知识检索合为一体。**

**根据**:
- 数字阅读已从"能看就行"进化到"读了能问",但市面上主流产品仍将阅读器和 AI 能力分属不同功能模块,没有打通"正读到某段 → 立刻针对这段提问"的闭环;
- 移动互联内容平台的典型形态是前后端分离 + 多微服务协作,书域采用的就是这个架构——Android App 做阅读端,Spring Boot 微服务做后端,事件驱动做跨服务通信;
- 结课设计要求 Server + Client 两端完整,且明确要求 AI 应用情况说明——书域的 RAG 读书问答直接对应这项要求。

**例子**:读者读到《西游记》第一回里一句"灵根育孕源流出",划词提问"灵根在这里指什么",AI 服务从已入库的章节向量中检索相关段落,结合大模型给出带原文引用的回答——这不是"搜全书",而是"搜当前上下文",精度远高于通用搜索。

## 二、开发目标

**三类用户各有一条主线:游客能浏览书城与公版书试读,读者能在自己书架上完整阅读并随时用 AI 提问,管理员能管理书籍内容与查看平台统计数据。**

**根据**(平台解决三个具体问题):
- **内容分散**:公版书散落在不同网站,格式各异(纯文本、扫描 PDF、网页连载)——书域将公版书统一入库,提供结构化章节与统一阅读体验;
- **阅读体验割裂**:在阅读 App 里看完一段想查背景,要切到浏览器搜索,回来已找不到刚才的段落——书域的 RAG 问答嵌入阅读器,选中即问,回答直接带原文定位;
- **无智能辅助**:传统电子书只提供"翻页 + 书签",没有理解文本内容的能力——书域用 Spring AI + 向量库给每本书建知识索引,让读者能"和书对话"。

**例子**:管理员通过书库服务 API 上传《三国演义》全书(章节 + 段落结构),向量化后读者可以在 App 中划词提问"曹操第一次出场时外貌描写是什么",AI 返回答案并附原文出处。

## 三、用户画像

### 画像一:通勤碎片阅读的学生

**小陈读公版书需要"零等待恢复 + 嵌入式 AI 提问",不靠书城推荐。**

**根据**:小陈是大二学生,每天地铁通勤 40 分钟。他对书的来源不挑剔(公版书足够),但对中断恢复的速度要求极高——从打开 App 到看到上次读的段落,中间不能超过 5 秒。偶遇文言文,需要即时解释,切到浏览器搜索就回不来了。

**例子**:他周二早高峰在地铁上打开书域 App,书架页最上方"继续阅读"卡片直接显示《鲁迅全集》读到第 3 卷第 12 页,点击即跳。读到"人固有一死,或重于泰山,或轻于鸿毛",长按选中,点"问问 AI",底部弹窗解释典故出处,前后 3 秒完成。

### 画像二:写读书笔记的内容创作者

**小李做论文引用需要"语义搜索 + 进度记录",不是关键词匹配。**

**根据**:研究生小李正在写论文,需要引用多本公版书原文。她的工作流是:读 → 标记关键段落 → 按主题检索 → 引用。关键词搜索("仁政")漏掉"以德治国"等同义表述;标记散落在不同 App 里,导出费时。

**例子**:她在书域中读完《论语》前五章,每章阅读进度被 ReadingProgress 事件记录——这意味着她之后查找"我最近读了哪些关于仁的内容"时,统计服务已经有数据基础,不需要她手动维护一个"已读清单"。
