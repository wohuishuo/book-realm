# 书域 v1 需求与验收清单

> **结论先行**:书域 v1 只证明一件事——一个读者能在手机上登录、找书、阅读,系统能记录行为,并能基于原文给出一次 AI 辅助理解。除此之外的功能先不做,否则项目会膨胀到无法讲清。

## 一、v1 一分钟说明

书域 v1 是一个移动端电子书学习项目:

读者用用户中心账号登录 Android App,从书库搜索并打开公版书,加入书架后阅读章节;阅读过程会把登录和进度交给统计服务;读者也可以请求 AI 对章节做摘要或围绕原文问答。

这句话能说清,才说明 v1 没散。

## 二、v1 必须完成什么

| 能力 | 用户能看到什么 | 后端发生什么 | 状态 |
| --- | --- | --- | --- |
| 登录 | App 用 `root / 12345678` 登录成功 | MVP-0 返回 JWT,并发布 UserLogin 事件 | ✅ 已完成 |
| 找书 | 书城搜索 `西游` 能看到《西游记》 | MVP-1 返回书籍列表 | ✅ 已完成 |
| 阅读 | 打开章节,能按段落阅读并调字号 | App 调 MVP-1 章节接口,本地保存字号/进度 | ✅ 已完成 |
| 书架 | 加入书架后重启仍可见 | Room 保存本地书架 | ✅ 已完成 |
| 登录统计 | 能查询每天 App/Web/Desktop 登录数量 | MVP-3 消费 UserLogin,聚合 LoginStats | ✅ 已完成 |
| 阅读进度统计 | App 阅读时上报进度,后端可查询 | MVP-3 接 `POST /api/stats/progress` | ✅ 已完成 |
| 章节摘要 | App 或 Swagger 能拿到章节摘要 | MVP-4 调 DeepSeek 或返回友好错误 | ✅ 已完成 |
| 原文问答 | 对一本书提问,回答带原文依据 | MVP-4 embed 段落并做 RAG 检索 | ✅ 已完成 |
| App 集成统计/AI | App 内能触发进度上报和 AI 摘要/问答 | MVP-2 调 MVP-3/MVP-4 HTTP API | ✅ 已完成 |

## 三、v1 明确不做什么

**结论:先砍掉会稀释主线的功能。** v1 不是商业阅读 App,而是课程项目的第一个完整闭环。

v1 不做:

- 支付、会员、充值、版权运营;
- 用户上传书籍、复杂书城推荐;
- 社交、书友匹配、评论区;
- 离线全文下载;
- 多端同步;
- AI 多轮长会话、知识库管理后台;
- 管理员复杂数据大屏。

这些可以进入 v1.1/v2,但不能挤进 v1。

## 四、MVP-3 的需求边界

> **结论先行**:MVP-3 只做"登录事件 + 阅读进度"两类统计。不要先做复杂 BI。

### 必须接口

| 接口 | 用途 | 验收 |
| --- | --- | --- |
| `GET /api/stats/logins?from=&to=` | 查询区间登录统计 | 发一条 App 登录事件后,当天 `appLogins +1` |
| `POST /api/stats/progress` | App 上报阅读进度 | 上报一次后,数据库出现 ReadingStats |
| `GET /api/stats/reading?from=&to=` | 查询阅读统计 | 能看到当天阅读次数/段落进度 |

### 必须消费者

- `LoginLogConsumer`:保存每次登录原始记录;
- `LoginStatsConsumer`:按日期和登录端类型聚合。

### 验收标准

- RabbitMQ 管理台能看到 `user.events` exchange 和两个队列;
- `mvn test` 证明事件能从 exchange 被消费并落库;
- 用户中心真实登录一次后,MVP-3 能看到统计变化;
- App 阅读进度上报失败不能影响阅读。

## 五、MVP-4 的需求边界

> **结论先行**:MVP-4 只做"摘要 + 有引用问答"。RAG 链路跑通比花哨 AI 功能重要。

### 必须接口

| 接口 | 用途 | 验收 |
| --- | --- | --- |
| `POST /api/ai/summary` | 章节文本摘要 | 有 key 时返回 100 字内摘要;无 key 时友好错误 |
| `POST /api/ai/embed` | 把一本书段落建索引 | embed 后文档数等于段落数 |
| `POST /api/ai/ask` | 基于原文问答 | 对《西游记》问题能返回相关段落引用 |

### 验收标准

- 无 `DEEPSEEK_API_KEY` 时服务仍能启动;
- 测试不依赖真实 LLM key;
- 回答必须尽量引用检索到的段落,不能只给泛泛而谈;
- 向量库实现通过 `VectorStore` 接口隔离,后续可换 PGVector。

## 六、App 集成边界

> **结论先行**:App 集成只做两个入口:阅读进度上报、AI 摘要/问答。不要把 App 重做成大而全。

### 必须改动

- 阅读器打开/滚动/退出时调用 `POST /api/stats/progress`;
- 阅读器增加"摘要"按钮,调用 `POST /api/ai/summary`;
- 阅读器增加"问一句"输入框,调用 `POST /api/ai/ask`;
- 无网络、无 key、AI 服务未启动时,显示清楚错误,不崩溃。

### 不做

- 不做复杂聊天记录;
- 不做流式输出;
- 不做登录统计大屏;
- 不做 AI 设置页。

## 七、v1 完成定义

v1 完成必须同时满足:

1. 五个仓库 main 分支干净,关键代码已 push;
2. 后端服务健康检查全绿:`80/8082/8083/8084`;
3. 手机 App 可登录、搜书、阅读;
4. 登录事件能进入 MVP-3 统计;
5. 阅读进度能从 App 上报到 MVP-3;
6. AI 摘要/问答至少在 Swagger 跑通,有 key 时能调模型,无 key 时不崩;
7. 平台书实战篇有 MVP-0~4 的教学章;
8. 技术图鉴能解释关键名词;
9. TODO 总进度更新到真实状态。

## 八、v1 后续整理顺序

**结论:代码闭环已经跑通,下一步重点是把平台变得更容易交付、复现和继续扩展。**

1. 做平台级 `docker compose`,把四个后端服务和依赖统一启动;
2. 给 Android App 补更完整的演示截图和使用说明;
3. 做一次全书 RC,清理重复说法、过期状态和章节顺序;
4. 选择 v1.1 功能,例如阅读历史、多书扩展、AI 多轮追问或管理端统计页。
