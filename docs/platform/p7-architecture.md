# P7 架构与技术选型

> **结论先行**:架构总图、技术选型表(为什么选它)、部署图。标注【待架构终审】的条目为初稿,最终选型由架构会话裁量。

## 一句话结论

**书域架构 = 1 个 Android 客户端 + 5 个 Spring Boot 微服务 + 1 个 RabbitMQ 消息队列 + 2 个数据库(MySQL 用户库/书库 + MySQL 统计库) + 1 个向量库 + 1 个 Redis 缓存——全部容器化,一条 `docker compose up` 拉起;技术选型的核心原则是"栈已验证过,不引入未知技术"。**

**架构要点**:
- 每个微服务独立端口、独立数据库(用户库 :3306 / 统计库 :3307,物理隔离);
- RabbitMQ 使用单一 exchange `bookrealm.events`,按消费方分 queue;
- App 通过 JWT 访问所有后端服务,服务间不直接调用(只通过事件解耦);
- 向量库未入图因选型待定【待架构终审】。

## 二、技术选型表

### 后端

| 项 | 选型 | 为什么是它而不是替代品 |
| --- | --- | --- |
| 语言 | Java 21 | 本机已装;课件要求 Java;Spring Boot 3 需要 Java 17+ |
| 框架 | Spring Boot 3 | 用户中心已验证;JPA + Security + Actuator 开箱即用;结课课件以 Spring Boot 为主线 |
| ORM | Spring Data JPA(Hibernate) | 用户中心已验证;自动建表;对 CRUD 场景足够;MyBatis-Plus 对简单实体过度 |
| 认证 | JWT(jjwt 库) | 用户中心已验证;无状态,适合 App ↔ 微服务;不需要 Session 同步 |
| 消息队列 | RabbitMQ | 结课训练课题原文指定;fanout 模式已演练过;比 Kafka 轻量(本平台事件量远不达 Kafka 门槛) |
| AI 框架 | Spring AI | 课件有专章;统一抽象(换 LLM 不改代码);内置 RAG 支持(VectorStore 接口) |
| LLM | DeepSeek | 国内可访问;性价比高;Spring AI 有适配 |
| 向量库 | SimpleVectorStore(内存) | Spring AI 内置实现,零运维;MVP 阶段演示用,后续可切 PGVector/Milvus;通过 VectorStore 接口切换,不改业务代码 |

**关于 Spring Cloud**:PPT 参考页提到的 Spring Cloud Gateway/Config Center 等组件适用于大规模微服务集群。书域只有 5 个简单服务,服务发现用 Docker Compose 内置 DNS 已足够;服务间 HTTP 调用量小,不需要断路器/分布式追踪。这符合课件"从简到繁,先单体后拆分"的思路,也避免了"为微服务而微服务"的过度设计。

### 前端(App)

| 项 | 选型 | 为什么是它而不是替代品 |
| --- | --- | --- |
| 语言 | Kotlin | Android 官方推荐;旧项目已是 Kotlin;Compose 需要 Kotlin |
| UI | Jetpack Compose | 声明式 UI,比 XML 开发效率高;本课要求的现代 Android 技术栈 |
| 本地存储 | Room | Android 官方 ORM;旧项目已有完整 Room 实体可迁移;比 SQLite 直接操作类型安全 |
| DI | Hilt | Android 官方推荐;Compose 原生集成;比 Koin 编译期安全 |
| 网络 | Retrofit + OkHttp | Android 网络层事实标准;JWT 拦截器已有模板 |
| Token 存储 | DataStore | 替代 SharedPreferences;支持协程;类型安全 |

### 基础设施

| 项 | 选型 | 为什么是它而不是替代品 |
| --- | --- | --- |
| 容器化 | Docker + Docker Compose | 用户中心已验证;一条命令起平台;结课要求"docker compose up" |
| 数据库 | MySQL 8 | 用户中心已验证;课件以 MySQL 为主;比 H2 文件数据库更适合演示 |
| 缓存 | Redis | 用户中心已验证(JWT 黑名单);scoop 已装;比内存缓存跨服务 |
| API 网关 | 无(暂不需要) | 平台仅 5 个服务,App 直接按域名+端口访问各服务;Docker Compose DNS 做服务发现已足够。Spring Cloud Gateway 适用于 10+ 微服务的大集群,对本书域规模属于过度设计。若结课文档展示需要,可在第 5 周加一个最小化 Nginx 作为统一入口 |

### 选型原则

**每项技术必须满足三个条件之一**(至少一个):
1. **已验证**:用户中心项目已用过(Spring Boot 3 / JWT / MySQL / Redis / Docker)
2. **课件要求**:结课训练课题指定(RabbitMQ fanout)、课件有专章(DDD / Spring AI)
3. **旧项目资产**:旧 Android 项目已有 Room 实体和 Hilt 注入模板

不满足任一条件的技术不引入。这避免了上学期"学满课件才动手→只完成数据库"的教训。

## 四、AI 应用情况说明

**结论:书域使用 DeepSeek 作为大语言模型,Spring AI 作为统一接入框架,RAG(检索增强生成)作为核心技术范式——将公版书章节文本向量化入库,读者选中任意段落提问时,AI 能从向量库中检索最相关的原文上下文,引用原文生成回答,避免 LLM"编造"书中不存在的内容。**

**根据**:
1. 结课设计说明明确要求"AI 应用情况说明",《专业训练课题》虽然未直接要求 AI,但课件有 Spring AI 专章,属于允许的技术栈;
2. Spring AI 1.0 提供了 VectorStore 抽象接口和 ETL pipeline(TokenTextSplitter / DocumentWriter),换模型和换向量库都不改业务代码;
3. DeepSeek 是国内可访问、性价比高的大模型,Spring AI 有官方适配;
4. AI 超级智能体参考项目的 RAG 教程验证了"本地向量库 + LLM 回答"技术路线的可行性(它的教程第 4、5 章完整覆盖了知识库搭建→检索→问答的全流程)。

**具体应用**:

| 应用点 | 技术实现 | 用户可见效果 |
| --- | --- | --- |
| RAG 读书问答 | 章节段落 → Embedding → SimpleVectorStore;用户划词提问 → 向量检索 Top-K → 组 Prompt → LLM 回答(含原文引用) | 阅读器中选中一段文字 → 点"问问 AI"→ 阅读器底部面板显示回答 + 原文出处 |
| 章节摘要 | 章节全文 → LLM 摘要 Prompt → 返回结构化摘要 | 阅读器工具栏"AI 摘要"按钮 → 弹出当前章节摘要 |
| 向量入库 | 管理员上传书籍 → 书库服务回调 AI 服务 → 批量 Embedding → 向量库 | 管理员操作,读者无感;上传完成后该书的 AI 问答即生效 |

## 五、技术关键点及解决方案

**结论:书域最出色的技术点是"RAG 读书问答嵌入阅读器"——它是移动阅读 App 中少见地将向量检索与大模型回答融入划词交互的实践;最关键的技术点是"登录事件驱动的分布式解耦"——它直接对应训练课题原文,且用 RabbitMQ fanout 模式干净地分离了认证与统计。**

### 关键点一:RAG 读书问答(最出色)

**业务功能**:读者在阅读器中选中一段文字(如文言文),AI 基于当前章节的向量库检索相关上下文,引用原文回答。

**约束与权衡**:
- 约束:LLM 会"编造"书中不存在的内容(hallucination);移动端网络不稳定,AI 调用延迟 >3s 即影响阅读流
- 决策:用 RAG 而非纯粹依赖 LLM 知识——先将书籍每个段落向量化入库,提问时检索最相关的段落作为"参考资料"喂给 LLM,强制它引用原文回答
- 降级:若向量库未覆盖当前章节,降级为仅用选中文本 + 问题发 LLM,不提供引用(示意:功能可用,精度略降)

**技术方案**(见 P6 图三顺序图):选中文本 + 章节 ID → AI 服务 → 向量库检索(按 chapterId 限定范围,避免跨章误检)→ LLM 生成回答 + 原文引用 → App 弹出面板。

### 关键点二:登录事件驱动的异步解耦(最关键,对应训练课题)

**业务功能**:用户登录后,认证服务只做两件事——返回 JWT + 发布 UserLogin 事件;日志和统计异步消费事件,登录过程不受后台处理影响。

**约束与权衡**:
- 约束:训练课题原文要求 fanout exchange + 两个独立 queue;登录响应时间必须 <1s(移动端体验红线)
- 决策:用户中心使用 RabbitMQ 的 fanout 模式发布事件——fanout 保证所有绑定的 queue 都收到消息;日志服务和统计服务各自消费自己的 queue,互不影响
- 关键技术细节:事件发布用异步线程(`@Async`),即使 RabbitMQ 宕机也不阻塞登录流程(事件入本地缓冲,重试 3 次后写入死信队列)

**技术方案**(见 P6 图一顺序图):登录成功 → UserLogin 事件发布到 exchange `bookrealm.events` → fanout 到两个 queue —— `login.log`(日志服务消费,落盘)和 `login.stats`(统计服务消费,聚合计数)。

### 关键点三:Room 离线缓存(最影响用户体验)

**业务功能**:读者首次在线加载章节后,内容缓存到 Room;下次打开同一章节直接读缓存,无需网络请求。

**约束与权衡**:
- 约束:章节内容可能被管理员更新(公版书校对后修正);缓存不能永久有效
- 决策:首次打开 → 网络加载 → Room 缓存;再次打开 → 查 Room → 命中且未超过 7 天则直接渲染,否则重新拉取
- 缓存键 = chapterId + 缓存时间戳,清理策略:LRU(最近最少使用且过期 7 天的先删)

**技术方案**(见 P6 图二顺序图):App 查 Room(④) → 命中则直接渲染(⑤),未命中则网络加载(⑥⑦)→ Room 缓存(⑧)→ 渲染(⑨)。
