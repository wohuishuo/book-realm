# 行动计划 v2:超级项目「书域」—— 多 MVP 电子书平台 + 一本书

> **结论先行**:做一个**超级项目**——电子书平台,由 **5 个互相咬合、各自完整的 MVP** 组成:已完成的用户中心直接当登录微服务用,Spring Boot 做书库服务,Android Compose 做阅读 App,RabbitMQ 做事件驱动统计,Spring AI 做智能服务。**七成准备,三成代码**:先用一个完整的预备阶段把需求、用例、领域模型(DDD)做扎实,再按里程碑开工。每个 MVP 都走我们验证过的「实现→真实验证→commit→push→写进书」闭环。

配套方法论:《方法论-从用户中心项目提炼.md》(同目录)。

## 〇、为什么是"多 MVP 超级项目"(对齐官方要求)

**结论**:这个形态不是我们拍脑袋,而是**结课设计说明的原文要求**与我们已有资产的最优交点。

**根据**(摘自《移动互联系统分析与设计结课设计说明》):

- 系统至少含 **Server 端 + Client 端**,前后端技术不限,手机 App / Web / 桌面端均可;
- 文档要求 **领域模型设计:业务实体、Service、领域事件、Bounded Context 划分与映射图**——这就是 DDD,课件里有《领域驱动设计》《微服务技术基础》;
- 架构图要求展示"**几个微服务、网关、消息队列(RabbitMQ)、几个数据库**";
- 明确要求 **AI 应用情况说明**(课件有 Spring AI);
- 《专业训练课题》原题就是:**登录触发 UserLogin 事件 → RabbitMQ fanout → 日志微服务 + 统计微服务**;
- 团队 2–4 人、五周完成、Git 分支协作、开发记录、项目总结 + AI 时代感悟。

**例子**:我们的用户中心已经是一个跑通的认证服务——它的登录接口加一行"发布 UserLogin 事件",就直接接上训练课题;阅读 App 用它的 JWT 登录,就满足 Server+Client。**已有资产全部变成超级项目的零件。**

## 一、超级项目地图:5 个 MVP

每个 MVP 的标准:**独立可运行、有自己的数据、有完成定义(DoD)、单独可演示**——任何一个被砍掉,其余照常工作。

| # | MVP | 技术 | 一句话定位 | 状态 |
| --- | --- | --- | --- | --- |
| 0 | **用户中心**(认证服务) | Spring Boot 3 + MySQL + Redis + JWT | 平台统一登录;所有客户端都从这里拿 JWT | ✅ **已完成**(复用) |
| 1 | **书库服务** | Spring Boot 3 + Spring Data JPA + MySQL + 文件服务 | 图书/章节内容 API + 封面与文本文件存取 | 新建 |
| 2 | **阅读 App** | Kotlin + Jetpack Compose + Room + Hilt + Retrofit | 书架/书城/阅读器;登录走 MVP-0,内容走 MVP-1,Room 离线缓存 | 新建(旧数据层迁移) |
| 3 | **事件驱动统计** | RabbitMQ + 两个 Spring 微服务 | UserLogin / ReadingProgress 事件 → 日志服务 + 统计服务(=训练课题原题) | 新建 |
| 4 | **AI 服务** | Spring AI + DeepSeek + **RAG** | 书籍摘要 + **读书问答(章节入向量库,引用原文回答)** | 新建 |
| 5 | (可选)书友匹配 | Spring Boot + Redis + 标签算法 | 按喜欢的书的标签匹配书友(参考伙伴匹配) | 备选 |

**协作关系**(架构总图的雏形,亦是结课文档要求的图):

```
┌─────────────┐     JWT      ┌──────────────┐
│ 阅读App(2)  │ ───────────> │ 用户中心(0)  │──发布 UserLogin 事件──┐
│ Compose     │              └──────────────┘                      ▼
│             │   章节/封面   ┌──────────────┐              ┌─────────────┐
│ Room 离线   │ ───────────> │ 书库服务(1)  │              │ RabbitMQ(3) │
└─────────────┘              │  JPA + 文件   │              │  fanout     │
      │ 摘要/问答             └──────────────┘              ├──→ 日志服务  │
      ▼                                                    └──→ 统计服务  │
┌─────────────┐                                                  ↓
│ AI 服务(4)  │                                              MySQL(统计库)
└─────────────┘
   全部容器化:docker compose 一键起平台(复用上次的编排经验)
```

**Bounded Context 划分**(领域模型的骨架):用户 BC(MVP-0)/ 书库 BC(MVP-1)/ 阅读 BC(MVP-2 的进度、书架)/ 统计 BC(MVP-3)/ AI BC(MVP-4)。BC 之间只通过 **API 或事件**交换信息——这张映射图就是结课文档的核心图。

## 二、七成准备:预备阶段 P(先做完,再写代码)

**结论**:P 阶段产出**全部需求与设计文档**,它们直接就是结课要交的东西——准备即交付,不白做。

| 步骤 | 产出 | 对应结课要求 |
| --- | --- | --- |
| P1 业务定位 | 业务领域、开发目标、用户画像 | 可行性与需求分析 |
| P2 竞品分析 | 起点读书 / 微信读书 / 番茄小说 对比表(优劣势) | 竞品分析 |
| P3 功能分解 | 功能层次树(每个 MVP 一棵子树) | 功能分解层次图 |
| P4 用例分析 | UML 用例图 + 用户类型与权限(游客/读者/管理员) + 核心用例规约 | 用例图与场景方案 |
| P5 领域模型 | 实体/Service/领域事件清单、UML 类图、包图、**BC 划分与映射图** | 领域模型设计(DDD) |
| P6 动态建模 | 2–3 张顺序图/活动图(登录事件流、打开一本书、AI 问答) | 系统动态特性 |
| P7 架构与选型 | 架构总图、技术选型表(写清"为什么选它")、部署图 | 系统设计文档 |
| P8 计划 | 分工表、五周时间轴、风险清单 | 项目开发与流程管理 |

P 阶段同样用金字塔写法写进书(理论篇新增 **DDD 章**,课件《领域驱动设计之程序员视角》为底);写完逐项检查逻辑链。

**P 阶段完成定义**:8 项产出齐全 + 团队(或自己)能用**一分钟**讲清整个平台 → 才允许进入编码。

## 三、三成代码:里程碑(每个 MVP 一组迷你 M)

沿用「实现→真实验证→commit→push→写进书」节奏。顺序按**依赖关系**排:

### 第 1 周 · P 阶段(上表)+ 环境
- 环境:Android Studio + 模拟器;RabbitMQ(scoop 有);确认 user-center 的 docker compose 还能一键起;
- 仓库:本目录 `git init` + GitHub 新仓库;书骨架从 user-center 搬入并改造(导航/配色/写作规范原样复用)。

### 第 2 周 · MVP-1 书库服务 + MVP-2 App 骨架
- 书库:JPA 实体(Book/Chapter,旧 Room 设计翻译过来)→ 内容 API → 种子数据(公版书)→ Swagger 实测;
- App:Compose 空壳 + Hilt + Navigation + 主题 → 模拟器跑通;
- **DoD**:`GET /books` 返回种子书;App 三个空 Tab 可切换。

### 第 3 周 · MVP-2 核心:登录 + 书架 + 阅读器
- 登录页对接**用户中心**(JWT 存 DataStore)——平台第一次"咬合";
- 书架(Room 缓存书库数据)→ 阅读器(章节渲染、进度记忆、字号);
- **DoD**:真机/模拟器走通"登录 → 书架 → 读一章 → 退出重进回到原位"。

### 第 4 周 · MVP-3 事件驱动 + MVP-4 AI
- 用户中心登录方法发布 UserLogin 事件(带登录类型:App/Web)→ RabbitMQ fanout → 日志服务落盘 + 统计服务写库(训练课题原题,可直接当一次作业交);
- App 阅读进度发 ReadingProgress 事件 → 统计服务聚合"读了多少章";
- AI 服务:Spring AI 接 DeepSeek,先做一个接口:`POST /ai/summary`(给章节文本返回摘要),App 阅读器加"AI 摘要"按钮;
- **DoD**:登录一次,统计库计数 +1 且能查"手机登录 X 次";阅读器里能弹出 AI 摘要。

### 第 5 周 · 测试 + 文档 + 部署 + 收尾
- 测试:各服务单元/集成测试 + App 的 ViewModel 测试与 1–2 个 Compose UI 测试;
- 部署:平台级 `docker-compose.yml`(用户中心 + 书库 + RabbitMQ + 日志 + 统计 + AI + MySQL + Redis),App 出签名 APK;
- 文档:按结课模板汇编(P 阶段产出 + 开发记录 commit 截图 + 项目总结 + **AI 时代感悟**——我们整个工作流本身就是最好的素材);
- 书:功能演示幻灯片(平台版)+「本章的真实代码」全部链好,上线 GitHub Pages;
- **DoD**:一条命令起平台 + APK 装手机能用 + 文档零缺项。

> **砍单原则**(时间不够时按序砍,每砍一个平台仍完整):AI 服务 → 阅读进度事件(保留登录事件)→ 书城搜索(保留书架+阅读器)。**用户中心、书库、App 主线、登录事件四样是底线。**

## 四、仓库与书:星系结构(1 个枢纽 + 每 MVP 一仓一书)

**结论**:**每个 MVP 一个独立 Git 仓库,每仓自带一本书**(代码+书同仓,沿用 user-center 模式);另设一个**平台枢纽仓**当"太阳",放总纲、共享知识和平台编排。书分两层,各写各的,不重复。

### 仓库清单

| 仓库 | 内容 | 书 |
| --- | --- | --- |
| **book-realm**(枢纽) | P 阶段全部文档、平台架构/BC 映射图、平台级 docker-compose(编排所有服务)、各仓索引 | **平台书**(总纲) |
| user-center-team-project | ✅ 已存在,不动 | ✅ 已有书 |
| br-library-service | 书库服务代码 | 书库小书 |
| br-reader-app | Android App 代码 | App 小书 |
| br-event-stats | RabbitMQ + 日志 + 统计服务 | 统计小书 |
| br-ai-service | Spring AI + RAG | AI 小书 |

**根据**:仓库边界=BC 边界=书的边界,三者对齐,每个 MVP 才真正"独立完整、单独可演示";枢纽仓解决"分散后看不到全貌"的问题。

### 两层书的分工(避免每本书重复造轮子)

- **平台书**(枢纽仓):方法论与写作规范(唯一正本)/ 理论篇(软件工程、**DDD**、架构与微服务)/ P 阶段需求与领域设计 / 平台架构总图 / 多服务联调 / 文档工坊(对照《结课设计说明》);
- **MVP 小书**(各仓):只写**自己领域**的内容——本 MVP 的定位与接口契约 / 里程碑实战章(含「本章的真实代码」)/ **只放本仓新技术的技术卡**(如 App 书放 Compose/Room/Hilt 卡,AI 书放 Spring AI/RAG 卡);
- **铁律**:讲方法论、讲平台架构 → 链接到平台书,小书不复制正文;小书之间互链接口契约页。

### RC 阶段:每本书的"重读整理"里程碑(必经)

**结论**:每本书的生命周期是 **初稿(随码随写)→ 冷却 ≥2 天 → AI 初审 → 人按清单终审 → 修订 → `git tag v1.0`**。金字塔搭完必须从上往下重走:只读每章结论句,看它们能否连成通顺的故事。

清单见同目录《**书的重读整理清单.md**》(三层:逐章逻辑链 / 全书递进与去重 / 跨书术语与接口一致),**复制进每个仓库**;RC 不做完,该 MVP 不算交付。第五周统一给全部书做跨书层检查。
