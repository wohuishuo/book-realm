# P8 分工与计划

> **结论先行**:五周时间轴以依赖关系排序——P 阶段先行,书库 + App 骨架打基础,App 咬合认证,事件 + AI 加亮点,测试部署收尾。每条风险有具体对策。

## 一、五周时间轴

| 周次 | MVP | DoD(可观察事实) |
| --- | --- | --- |
| 第 1 周 | 枢纽 | P1–P8 齐全;环境就绪;`docker compose up` 一键起;平台书可构建 |
| 第 2 周 | MVP-1/2 | 书库:`GET /books` 返回种子书;App:Compose+Hilt+Navigation,三个空 Tab 可切换 |
| 第 3 周 | MVP-2 | 登录对接(JWT→DataStore);书架(Room+"继续阅读"卡片);阅读器(渲染+进度记忆);真机走通"登录→书架→读一章→退出重进回到原位" |
| 第 4 周 | MVP-3/4 | UserLogin→fanout→日志+统计,查"手机登录 X 次";AI 摘要+RAG 问答,阅读器弹面板 |
| 第 5 周 | 全部 | 各服务测试;docker-compose 全平台;APK;文档汇编;书上线 GitHub Pages |

**根据**:时间轴与 plan.md 第三节里程碑一致——每周的 DoD 都是可观察事实(接口返回数据、模拟器截图、统计库计数),不靠感觉判断"做完没"。

## 二、风险清单

| 风险 | 对策 |
| --- | --- |
| **R1** 环境问题(RabbitMQ/Docker/模拟器) | 第 1 周预留整日验证;RabbitMQ 走 scoop(Docker 备选);模拟器闪退降级真机 USB;2h 无解写 BLOCKED.md |
| **R2** 用户中心与 App 对接失败 | 第 3 周前用 Postman 单独验证 API;接口契约已在 P4 明确;若格式有出入改 App 拦截器(不改用户中心) |
| **R3** AI RAG 超预期复杂度 | 先做摘要(不依赖向量库)保底;RAG 先跳过向量检索保证流程跑通;第 4 周末仍不通触发砍单 |
| **R4** 时间不足连锁延迟 | 周末进度检查;严格按砍单顺序;底线四件套(用户中心+书库+App 阅读器+登录事件)优先级最高 |
| **R5** Compose 多容器编排复杂 | 复用 user-center compose 模板;每加一个服务即验证;不顺则降级为分别 `docker run` |

**例子**:R3 的具体含义——第 4 周周三,若向量库还没搭好,就先把 `/api/ai/ask` 做成"选中文本+问题直接发 LLM,不检索",功能可用,引用功能暂时缺失,第 5 周再补。

## 三、砍单顺序

**结论:按依赖和重要度排序,每砍一个平台仍完整。**

| 序号 | 砍掉 | 触发条件 | 后果 |
| --- | --- | --- | --- |
| 1 | MVP-5 | 第 1 周结束 | 无影响 |
| 2 | MVP-4 摘要(留 RAG) | 第 4 周 AI 滞后 | RAG 问答仍是亮点 |
| 3 | MVP-3 阅读进度(留登录) | 第 4 周统计滞后 | 登录事件已满足训练课题 |
| 4 | MVP-2 书城搜索(留书架+阅读器) | 第 3 周 App 滞后 | 靠最近阅读和书名直达 |

**底线**:用户中心 + 书库 API + App 书架阅读器 + 登录事件。缺任一样平台不完整。
