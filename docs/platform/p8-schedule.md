# P8 分工与计划

> **结论先行**:分工表、五周时间轴、风险清单与砍单顺序。

## 一句话结论

**五周时间轴以依赖关系排序——P 阶段先行,书库 + App 骨架打基础,App 核心咬合认证,事件 + AI 加亮点,测试部署收尾——每条风险都有具体对策,砍单顺序从可选 MVP-5 逐级下砍至底线四件套。**

## 一、五周时间轴

| 周次 | 里程碑 | MVP 对应 | 具体产出(DoD) |
| --- | --- | --- | --- |
| 第 1 周 | P 阶段 + 环境 | 枢纽 | P1–P8 文档齐全;环境就绪(Android Studio + 模拟器 + RabbitMQ);user-center docker compose 一键起;平台书可构建上线 |
| 第 2 周 | 书库 + App 骨架 | MVP-1 / MVP-2 | 书库:JPA 实体(Book/Chapter/Paragraph)、内容 API、种子数据(公版书)、Swagger 实测 `GET /books` 返回种子书;App:Compose 空壳 + Hilt + Navigation + 主题,三个空 Tab 可切换 |
| 第 3 周 | App 核心:登录 + 书架 + 阅读器 | MVP-2 | 登录页对接用户中心(JWT → DataStore);书架(Room 缓存书库数据 → 最近阅读卡片);阅读器(章节渲染、进度记忆、字号调节);真机/模拟器走通"登录 → 书架 → 读一章 → 退出重进回到原位" |
| 第 4 周 | 事件驱动 + AI | MVP-3 / MVP-4 | 登录事件:UserLogin → RabbitMQ fanout → 日志落盘 + 统计写库,查"手机登录 X 次"可见;阅读进度事件:ReadingProgress → 统计聚合"读了多少章";AI 服务:摘要接口 + RAG 问答接口,阅读器内可弹问答面板 |
| 第 5 周 | 测试 + 部署 + 收尾 | 全部 | 各服务单元/集成测试;App ViewModel 测试 + 1–2 个 Compose UI 测试;平台级 docker-compose.yml(全部容器一条命令起);App 出签名 APK;文档汇编(结课模板);书上线 GitHub Pages;RC 逐章检查 |

## 二、风险清单

| 序号 | 风险 | 概率 | 影响 | 具体对策 |
| --- | --- | --- | --- | --- |
| **R1** | 环境问题导致开发停滞(RabbitMQ 装不上、Docker 起不来、模拟器闪退) | 中 | 高 | ①第 1 周预留整日做环境验证:按 user-center 的 DEV-SETUP.md 逐项复验;②RabbitMQ 走 scoop(Docker 镜像备选);③模拟器若闪退,降级用真机 USB 调试;④排查 2 小时无解立即在 BLOCKED.md 记录并求助 |
| **R2** | 用户中心与 App 集成对接失败(API 不兼容、JWT 格式不一致) | 低 | 高 | ①第 3 周登录对接前,先用 Postman/Swagger 单独验证用户中心 API 返回格式;②用户中心已稳定,接口契约已在 P4 明确;③若格式有出入,改 App 侧拦截器适配(不改用户中心,因其已冻结) |
| **R3** | AI 服务 RAG 实现超预期复杂度(向量库选型纠结、LLM 调用不稳定) | 中 | 中 | ①第 4 周 AI 服务先做摘要接口(不依赖向量库)作为保底;②RAG 问答先硬编码"给定章节 + 问题"的 prompt 路径(跳过向量检索)确保流程跑通;③若第 4 周末仍不通,触发砍单:AI 只保留摘要,RAG 降级为"未来升级" |
| **R4** | 时间不足:某周任务未完成导致后续周连锁延迟 | 高 | 高 | ①每周末做进度检查:该周 DoD 未完成 → 当周压缩非核心(如测试、UI 打磨);②严格按砍单顺序执行;③底线四件套(用户中心+书库 API+App 阅读器+登录事件)优先级最高,其他均可砍 |
| **R5** | 部署阶段 docker compose 编排复杂(多个 Dockerfile、网络、卷挂载协调) | 中 | 中 | ①复用 user-center 的 docker-compose.yml 模板(网络、MySQL、Redis 配置已验证);②每新增一个服务即加进 compose 并验证,不一性等到第 5 周;③若第 5 周仍编排不顺,降级为分别 `docker run` 逐个服务(功能等价,只是多几条命令) |

## 三、砍单顺序及触发条件

| 砍单序号 | 砍掉内容 | 触发条件 | 后果与补救 |
| --- | --- | --- | --- |
| 1 | MVP-5 书友匹配 | 第 1 周结束即搁置(本来就排不进五周) | 无影响。设计文档已占位,可做答辩"后续规划" |
| 2 | MVP-4 AI 摘要(保留 RAG 问答核心) | 第 4 周中期 RAG 问答跑通但摘要未开发 | RAG 问答仍是亮点,摘要在答辩中描述为"架构已预留" |
| 3 | MVP-3 阅读进度事件(保留登录事件) | 第 4 周中期登录事件已通但进度事件开发滞后 | 登录事件已满足训练课题原文要求(Login → fanout → 日志+统计) |
| 4 | MVP-2 书城搜索(保留书架+阅读器) | 第 3 周末书架和阅读器已通但搜索未做 | 用户可通过"最近阅读"卡片和书库 API 直接获取书籍列表,不影响核心闭环 |

**底线(不可砍)**:用户中心认证(MVP-0) + 书库 API(MVP-1) + App 书架与阅读器主线(MVP-2) + 登录事件(MVP-3 核心) — 这四样构成"能登录 → 能读书 → 能统计"的最小闭环,缺任何一样平台不完整。

> 团队 2–4 人,组员信息由用户自行填写。以下按 MVP 建议分工,每个人可负责 1–2 个 MVP。

| 成员 | 角色 | 负责 MVP | 主要任务 |
| --- | --- | --- | --- |
| **(待填)** | 后端主力 | MVP-1 书库服务 + MVP-3 事件驱动 | Spring Boot 实体与 API;RabbitMQ 生产者/消费者;docker compose 编排 |
| **(待填)** | 前端主力 | MVP-2 阅读 App | Compose UI(书架/书城/阅读器);Room 缓存;Retrofit 对接后端 |
| **(待填)** | 全栈/AI | MVP-4 AI 服务 + MVP-0 集成 | Spring AI + RAG;向量库搭建;用户中心 JWT 对接 |
| **(待填)** | 测试/文档(可选) | 全平台 | 测试用例;结课文档汇编;书 RC 审查 |

**协作约定**:
- 代码仓库按 MVP 分仓,每人在自己仓库开发,接口通过 Swagger/契约文档对齐;
- 每日同步一次(口头或群聊):"今天做了什么,遇到什么阻塞,明天做什么";
- 每次合并前在本地验证 `docker compose up` 全平台起得来;
- 第 4 周和第 5 周各做一次全平台联调。
