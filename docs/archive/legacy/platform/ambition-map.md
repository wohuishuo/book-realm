# BookRealm 能力野心地图

> **结论先行**:BookRealm 的长期目标不是“做一个够用的阅读 App”,而是做一个能展示完整工程能力的阅读平台。别人有的能力,我们可以逐步拥有;别人没有的能力,我们也可以做实验。但所有能力必须拆成小 MVP,每个 MVP 都要能独立说明、独立验证、独立维护。

## 一、一分钟说明

BookRealm 要成为一个“阅读平台能力展厅”:

读者看到的是舒服、聪明、有惊喜的阅读产品;开发者看到的是 Android、Spring Boot、AI、TTS、推荐、导入、社区、支付、控制台、可观测性、CI/CD、文档和团队协作的完整工程样板。

这不是盲目堆功能。原则是:功能可以多,但边界不能乱;UI 可以超出想象,但交互不能失控;技术可以企业级,但每一步都要能跑、能测、能讲清。

## 二、总原则

| 原则 | 含义 | 例子 |
| --- | --- | --- |
| 小 MVP 切片 | 每次只交付一个能演示的闭环 | 先做本地 TTS,再做服务端 Qwen3-TTS,最后做音频缓存和通知栏 |
| 能力可拆 | 每个大功能都能独立成服务或模块 | 推荐服务、TTS 服务、导入服务、控制台 |
| 体验先行 | 用户真正用到的页面优先 | 阅读器、书架、详情页、选区菜单 |
| 企业级约束 | 有测试、日志、错误处理、配置、文档 | 不是“能跑一次”,而是“坏了知道哪里坏” |
| 公开可讲 | 每个能力都写进平台书 | 让别人看 README 和书就知道你做了什么 |
| 不做违法/侵权 | 不抓取版权不清内容,不做恶意功能 | 书源规则可以研究,但 v2 不做盗版聚合 |

## 三、能力分层

### A. 阅读体验层

**结论:这是最先显得“像产品”的部分。**

能力池:

- 书架列表/网格;
- 最近阅读;
- 书籍详情长页;
- 目录、进度、章节跳转;
- 横排/竖排;
- 分页/连续滚动;
- 主题、字号、行距、字体;
- 选区菜单;
- 划线、笔记、段评;
- 词典弹窗;
- 听书浮层。

交付顺序:

1. v2.1 阅读器成型;
2. v2.2 选区、划线、笔记;
3. v2.3 听书;
4. v2.x 竖排、词典、跟读体验增强。

### B. AI 阅读层

**结论:AI 不是聊天按钮,而是阅读流程里的第二大脑。**

能力池:

- 当前段落解释;
- 章节摘要;
- 整本书问答;
- 选中文字问 AI;
- AI 生成读书卡片;
- AI 根据笔记生成复习题;
- AI 推荐下一本书;
- AI 帮用户整理书摘;
- AI 对导入 PDF/EPUB 自动分章、摘要、打标签。

交付顺序:

1. 已完成:摘要 + RAG 原文问答;
2. v2.2:选区 AI 解释;
3. v2.x:读书卡片和笔记整理;
4. v3:个性化推荐和学习路径。

### C. 内容导入层

**结论:内容导入决定平台能不能从 demo 变成真实可用。**

能力池:

- EPUB 导入;
- TXT 导入;
- 文字型 PDF 导入;
- 扫描 PDF OCR;
- 自动分章;
- 自动抽取目录;
- 封面识别;
- 私有书库;
- 导入后也能划线、笔记、AI 问答。

交付顺序:

1. EPUB;
2. TXT;
3. 文字型 PDF;
4. OCR;
5. 批量导入和管理台审核。

### D. TTS 与音频层

**结论:听书要从“能发声”升级到“像播放器一样可靠”。**

能力池:

- Android 本地 TTS;
- 服务端 Qwen3-TTS;
- 音色选择;
- 语速、定时关闭;
- 当前段落跟读;
- 通知栏媒体控制;
- 音频缓存;
- 章节批量生成;
- VoiceClone 实验模式;
- 系统小组件/厂商状态栏能力。

交付顺序:

1. 本地 TTS;
2. `br-tts-service`;
3. 音频缓存与任务队列;
4. 通知栏/小组件;
5. VoiceClone 实验室。

### E. 社区互动层

**结论:社区不是先做广场,先从段落评论开始。**

能力池:

- 段评;
- 笔记点赞;
- 回复;
- 书评;
- 书友圈;
- 关注用户;
- 读书小组;
- 推荐动态流;
- 举报和审核。

交付顺序:

1. 段落笔记;
2. 点赞/回复;
3. 书评;
4. 书友圈;
5. 审核和反垃圾。

### F. 推荐与搜索层

**结论:推荐先可解释,再算法化。**

能力池:

- 关键词搜索;
- 标签推荐;
- 最近阅读;
- 同类作品;
- “读过这本的人也读”;
- 语义搜索;
- 向量召回;
- 排序模型;
- 推荐原因解释;
- A/B 实验。

交付顺序:

1. 搜索和标签;
2. 规则推荐;
3. 语义搜索;
4. 行为推荐;
5. 实验平台。

### G. 商业与运营层

**结论:支付/会员可以做,但先做成工程能力演示,不要伪装成真实商业系统。**

能力池:

- 会员状态;
- 订单;
- 支付回调模拟;
- 权益校验;
- 优惠券;
- 积分;
- 活动页;
- 审计日志;
- 风控占位。

交付顺序:

1. 会员/订单数据模型;
2. 沙箱支付或模拟支付;
3. 权益校验;
4. 管理台查看订单;
5. 活动和优惠券。

### H. 管理与企业级工程层

**结论:企业级不是页面多,而是系统可维护、可观测、可恢复。**

能力池:

- Admin 控制台;
- 用户管理;
- 书籍管理;
- 导入任务管理;
- AI/TTS 调用统计;
- 日志查询;
- 错误追踪;
- 指标监控;
- CI/CD;
- Docker Compose;
- 配置中心;
- 权限系统;
- 审计日志;
- 数据备份。

交付顺序:

1. Admin Web;
2. 统计看板;
3. 日志和错误页;
4. Compose 一键启动;
5. CI/CD 与部署文档。

## 四、MVP 命名规则

**结论:以后不要用“做一大堆功能”描述任务,要用可交付 MVP 命名。**

| 编号 | 名称 | 目标 |
| --- | --- | --- |
| v2.1 | 阅读体验 MVP | 让 App 像真实阅读器 |
| v2.2 | 笔记互动 MVP | 划线、笔记、段评、词典、AI 解释 |
| v2.3 | 听书 MVP | 本地 TTS + 服务端 TTS 设计 |
| v2.4 | 控制台 MVP | 看见用户、书、阅读、AI、错误 |
| v2.5 | 导入 MVP | EPUB/TXT/PDF 进入书库 |
| v2.6 | 推荐 MVP | 标签、规则、AI 推荐理由 |
| v2.7 | 商业能力 MVP | 会员、订单、模拟支付、权益 |
| v2.8 | 社区 MVP | 书评、书友圈、审核 |
| v3.0 | 平台化 MVP | 多端、插件、实验室、企业级部署 |

## 五、验收标准

每个小 MVP 必须同时满足:

1. App 或 Web 有可演示入口;
2. 后端接口有 Swagger 或 README;
3. 数据库表有设计说明;
4. 关键逻辑有测试;
5. 失败状态能看懂;
6. 平台书有实战章或设计章;
7. README 写清如何启动;
8. GitHub main 分支干净并 push;
9. TODO 总进度更新。

## 六、对外展示方式

**结论:实力不是靠功能名堆出来,而是靠“能打开、能演示、能解释、能维护”。**

作品集展示时,不要说“我做了很多功能”,而是这样讲:

- 这是一个跨平台阅读平台;
- Android App 提供真实阅读体验;
- Spring Boot 微服务拆分认证、书库、统计、AI、TTS、导入、控制台;
- RabbitMQ 承载事件流;
- DeepSeek/RAG 让回答基于原文;
- Qwen3-TTS 负责高质量朗读;
- 每个模块都有 README、测试、实战章节和运行方式;
- 项目按小 MVP 迭代,不是一次性堆出来。

这才是“实力非凡”的表达方式:别人看到的不只是想法多,而是你能把复杂系统拆开、做完、讲清、持续维护。
