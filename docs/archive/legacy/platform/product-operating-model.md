# BookRealm 项目治理地图

> **结论先行**:BookRealm 是一个产品,不是五个 MVP 的集合。用户中心、书库、阅读 App、事件统计和 AI 服务是五个产品能力/可部署组件;它们共同交付一条端到端阅读价值链。

## 一、统一层级

**结论**:以后统一使用“产品 → 产品里程碑 → PRD → 产品能力 → 仓库 → Issue”的层级,避免把版本、模块和仓库混为一谈。

| 层级 | 回答的问题 | BookRealm 示例 |
| --- | --- | --- |
| 产品 | 我们长期在建设什么 | BookRealm 阅读平台 |
| 产品里程碑 | 这一阶段要证明什么 | MVP、Alpha、Beta、1.0 |
| PRD | 用户为什么需要这项结果 | 找书与入架、沉浸阅读、阅读标记、AI 原文问答 |
| 产品能力 | 哪个稳定边界负责实现 | 身份、内容、客户端、统计、AI |
| 仓库 | 代码在哪里独立构建和发布 | `user-center-team-project`、`br-library-service` 等 |
| Issue | 本次具体交付什么 | 给书库接口补 JWT 校验和越权测试 |

**例子**:“用户重新打开书后恢复上次位置”属于阅读连续性 PRD;它由阅读 App 和统计能力共同实现,可能同时产生 Android、API 和测试三个 Issue,但不会因此创建三个 MVP 或三个新仓库。

## 二、MVP 与 PRD 的关系

**结论**:一个产品先用 MVP 验证最小价值,通过后进入 Alpha、Beta 和正式版本;一个 MVP 通常包含多个围绕同一验证目标的 PRD,PRD 会在后续版本继续演进。

BookRealm 的第一个真正 MVP 应定义为:

> 读者能登录、找到一本书、加入书架、完成阅读并恢复进度;遇到不懂的原文时能获得有引用的 AI 帮助。

建议把现有能力整理成以下 PRD,编号后续确定:

| PRD | 用户结果 | 主要能力 |
| --- | --- | --- |
| 身份与会话 | 安全登录并保持会话 | 用户中心、App |
| 找书与书架 | 找到书并保存到个人书架 | 书库、App |
| 阅读连续性 | 阅读、调整样式并恢复位置 | App、统计 |
| 阅读标记与互动 | 划线、笔记、段评和点赞 | App、书库 |
| AI 原文理解 | 摘要、提问并跳回引用原文 | App、AI、书库 |

**例子**:当前 `0.3.x-alpha` 是产品版本/里程碑,不是第六个仓库;“划线可删除”是阅读标记 PRD 下的验收项,不是独立 MVP。

## 三、仓库策略

**结论**:不要按 MVP 新建 Git 仓库;只在组件需要独立构建、发布、权限或复用时拆仓。现有六个正式仓库先保留,不为术语纠正搬代码。

| 仓库 | 定位 | 决定 |
| --- | --- | --- |
| `book-realm` | 产品总控、跨仓 PRD、平台 ADR、集成验收、在线工程书 | 保留为唯一产品正本 |
| `user-center-team-project` | 独立认证服务兼课程作品 | 保留独立仓 |
| `br-library-service` | 书籍、章节、标记与互动 API | 保留独立仓 |
| `br-reader-app` | Android 客户端和设计系统实现 | 保留独立仓 |
| `br-event-stats` | 登录/阅读事件和进度统计 | 保留独立仓 |
| `br-ai-service` | 摘要、检索和原文问答 | 保留独立仓 |

`br-design-book` 是设计研究资料,不是运行时仓库;旧 Android 工程和课程资料是参考输入,不能作为当前实现正本。

**例子**:一次“统一鉴权”交付会改四个代码仓,但只属于一个平台 ADR 和一组关联 Issue。仓库边界不跟着 Sprint 或 MVP 改名。

## 四、文档归属

**结论**:跨仓文档集中在 `book-realm`,组件实现细节留在各自仓库;不是所有文档物理上放在一起,而是所有入口和链接集中在一起。

| 文档 | 权威位置 |
| --- | --- |
| 产品愿景、路线图、PRD、版本范围 | `book-realm/docs/product/`(迁移目标) |
| 跨仓架构、平台 ADR、API 契约 | `book-realm/docs/architecture/`(迁移目标) |
| 集成测试、发布门、平台 Runbook | `book-realm/docs/quality/`(迁移目标) |
| 组件启动、局部设计、局部测试 | 对应组件仓 `README.md` 和 `docs/` |
| Android 设计令牌与组件用法 | `br-reader-app` |
| 竞品截图和设计研究 | `br-design-book` |
| 课程报告和用户中心教学书 | `user-center-team-project` |

迁移期间不立即移动 `docs/platform/`。先建立索引和“唯一权威来源”,再逐页迁移并保留重定向/链接,避免一次大搬家造成断链。

## 五、当前痛点

**结论**:当前最大的风险不是代码量,而是权威来源过多、术语错位和自动质量门不足。

1. `MVP` 同时表示模块、仓库、工程阶段和产品版本,沟通成本高。
2. `PRD`、`plan.md`、`TODO-总进度.md`、`project-memory.md` 都在描述当前状态,容易互相过期。
3. 总控仓只有文档部署 CI;三个后端仓和 Android 仓没有各自 CI。
4. 平台脚本能做后端冒烟,但 PR 上没有统一 lint、test、build 必过规则。
5. `ADR-001` 已识别鉴权风险,尚未落地,用户数据接口仍只适合 Alpha。
6. 产品设计资料丰富,但缺少“一条用户旅程 → PRD → Issue → PR → 测试证据”的追踪链。

**例子**:当前 `v1-scope.md` 仍用 `MVP-3/MVP-4` 指代统计和 AI 服务,而 `versioning.md` 又用 Alpha/1.0 描述产品成熟度;两套语言都合理,但混用后读者无法判断“版本”和“组件”的区别。

## 六、唯一权威来源

**结论**:每类事实只能有一个正本,其他页面只摘要并链接。

| 事实 | 正本 |
| --- | --- |
| 产品为什么做、给谁用 | Product Vision |
| 某项用户结果和验收 | 对应 PRD |
| 当前版本包含什么 | Release Scope / Roadmap |
| 为什么采用某架构决策 | ADR |
| 当前工作状态 | Linear;迁移前暂用 `TODO-总进度.md` |
| 服务接口 | OpenAPI/契约测试 |
| 非显然环境坑和长期约束 | Project Memory |
| 是否允许合并 | CI 状态 |

Memory 不存待办,PRD 不存每日进度,Linear 不替代架构决策,README 不复制完整需求。

## 七、Linear 工作模型

**结论**:Linear 管工作流,GitHub 管代码事实,文档管产品与决策;三者通过链接连接,不互相复制全文。

| Linear 对象 | BookRealm 用法 |
| --- | --- |
| Initiative | BookRealm 产品化与求职作品集 |
| Project | 一个产品里程碑,如“0.4 我的记录”或“统一鉴权” |
| Cycle | 1–2 周执行窗口 |
| Issue | 可在一个 PR 内验收的任务 |
| Label | `android`、`library`、`ai`、`docs`、`security`、`agent:codex` |

Codex 和 CC 不冒充真实员工账号。Issue 仍由人负责,用标签或评论记录由哪个 Agent 执行;人负责优先级、验收和最终合并。

## 八、重构顺序

**结论**:先重构信息和质量门,再重构代码;当前能运行的服务不因目录审美被重写。

1. 建立术语表、产品地图和文档索引,宣布唯一权威来源。
2. 把现有大 PRD 拆成 4–6 个用户结果 PRD,为每个 PRD补验收场景。
3. 把跨仓决策整理为 ADR 目录,先落地 ADR-001 统一鉴权。
4. 为四个代码仓建立 CI:`lint/check → unit test → build`;总控仓保留跨服务冒烟。
5. 接入 Linear,先导入“统一鉴权”和“0.4 我的记录”两个 Project,不导入全部历史噪声。
6. 以后每项改动走 `PRD/ADR → Linear Issue → feature branch → PR → CI → 人工验收 → 合并`。

**例子**:下一阶段不应“重写阅读 App”,而应先建立 Android CI 和真实点击冒烟,再按 PRD 验收项逐个修正阅读、标记和返回行为。
