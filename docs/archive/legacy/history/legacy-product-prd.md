# BookRealm 产品需求文档(PRD)

> **结论先行**:BookRealm 是一个面向课程展示和工程复盘的开源跨平台阅读平台。第一目标不是复制商业阅读 App,而是证明一条完整链路:读者能登录、找书、阅读、留下阅读痕迹,并让 AI 基于原文帮助理解。

## 1. 一分钟说明

**BookRealm 要让读者在手机上完成一次“读书 + 理解 + 记录”的闭环。**

读者登录 Android App,在书城搜索公版书,加入书架后打开章节阅读。阅读过程中,系统保存本地书架、离线章节、字号/主题/进度;后端记录登录与阅读进度;读者可以划线、写想法、发段评,也可以向 AI 提问,AI 必须优先基于书中原文给出依据。

这句话说不清,项目就散。所有功能都要回到这条主线。

## 2. 问题定义

**结论**:这个项目要解决的不是“做一个功能最多的 App”,而是“把一个现代软件工程项目讲清楚、跑起来、验收掉”。

| 问题 | 现象 | BookRealm 的回答 |
| --- | --- | --- |
| 课程项目容易只剩代码 | 看起来能跑,但需求、边界、生命周期讲不清 | 用 PRD、P 阶段、实战篇和工程治理把决策写下来 |
| 阅读 App 主链路复杂 | 登录、书库、阅读、统计、AI 很容易混成一团 | 拆成多个独立 MVP,每个仓库职责单一 |
| AI 容易脱离内容瞎答 | 读者问书,模型可能泛泛而谈 | RAG 先检索原文,回答必须带依据 |
| 体验问题反复返工 | 顶栏、返回、划线关闭等坑会重复出现 | 项目记忆库记录交互裁决,自动化测试逐步兜底 |
| 后端安全容易被忽略 | `userId` 客户端传参会越权 | ADR-001 统一鉴权作为下一阶段后端红线 |

## 3. 用户与场景

**结论**:BookRealm 有四类用户,每类用户关心的不是同一件事。PRD 要分别照顾他们。

| 用户 | 目标 | 关键场景 | 成功标准 |
| --- | --- | --- | --- |
| 普通读者 | 顺手读一本书 | 登录、找书、加入书架、阅读、划线、问 AI | 不看说明也能完成主链路 |
| 课程老师 | 看项目是否完整 | 检查需求、架构、代码、测试、演示 | 文档和代码能互相对应 |
| 团队开发者 | 接着开发不迷路 | 看 TODO、PRD、接口、Runbook | 能定位当前状态和下一工单 |
| 学习者 | 学现代工程方法 | 读实战篇和技术图鉴 | 知道每个技术为什么用、怎么验证 |

## 4. 产品目标

**结论**:目标分三层:能跑、可信、可继续长大。

| 层级 | 目标 | 衡量方式 |
| --- | --- | --- |
| v1 能跑 | 登录、找书、阅读、统计、AI 问答形成闭环 | 后端 `test-platform.ps1` 绿;App 真机可演示 |
| 0.3.x 可信 | 阅读体验不再频繁踩老坑 | 真机 smoke + 关键点击链路自动化 |
| 1.0 可交付 | 普通读者不用说明也能顺手完成主流程 | 主要功能有自动化验收;我的页/笔记/AI 历史可用 |

## 5. 范围

### 5.1 当前必须保住的主链路

**结论**:这些能力是 BookRealm 的骨架,不能为了新功能破坏它们。

| 编号 | 能力 | 当前状态 | 验收 |
| --- | --- | --- | --- |
| BR-01 | 用户登录 | 已接用户中心 | `root / 12345678` 可登录 |
| BR-02 | 搜书与详情 | 已接书库服务 | 搜 `西游` 能看到《西游记》并打开详情 |
| BR-03 | 书架 | 已有 Room 本地书架 | 加入后重启仍可见,可移出 |
| BR-04 | 阅读器 | 已能显示章节段落 | 能阅读、调字号/主题/行距、恢复进度 |
| BR-05 | 离线章节 | 已有章节缓存 | 已打开章节断网可回退本地缓存 |
| BR-06 | 划线/笔记/段评 | 第一版已接入 | 可划线、写想法、发段评、点赞 |
| BR-07 | 统计 | 已接事件统计 | 登录事件和阅读进度可查询 |
| BR-08 | AI 摘要/问答 | 已接 AI 服务 | 有 key 时生成回答;无 key 时返回检索依据 |
| BR-09 | 工程验收 | 后端一键验收已完成 | `start-platform.ps1`、`test-platform.ps1` 可用 |

### 5.2 当前明确不做

**结论**:不做这些不是能力不够,而是为了守住主线。

- 支付、会员、充值、版权运营;
- 小说站抓取、盗版内容聚合;
- 大规模推荐算法;
- 全站社区广场、复杂审核;
- 扫描 PDF OCR;
- 厂商级系统组件深度适配;
- 真实商业发布所需的隐私合规、灰度发布和运维体系。

## 7. 非功能需求

**结论**:课程项目也要有工程质量,否则功能越多越不可信。

| 类型 | 要求 | 当前状态 |
| --- | --- | --- |
| 可运行 | 每个服务可独立启动,平台可一键启动 | 后端已具备 |
| 可测试 | 后端有一键验收;App 有真机 smoke | App 仍需真实点击链路 |
| 可维护 | 服务分层一致,文档与代码互相引用 | 已具备基础 |
| 安全 | 用户数据必须由 token 身份决定 | 未完成,见 ADR-001 |
| 可恢复 | App 本地保存阅读设置和章节缓存 | 已具备基础 |
| 可解释 | AI 回答必须保留原文依据 | 已具备基础 |

## 8. 验收标准

**结论**:验收不是“看起来差不多”,而是机器和人各验一层。

### 8.1 机器验收

| 范围 | 命令 | 必须证明 |
| --- | --- | --- |
| 平台后端 | `./test-platform.ps1` | 登录、搜书、章节、划线、进度、AI 冒烟通过 |
| 平台书 | `npm run docs:build` | 文档链接和构建通过 |
| Android | `./gradlew testDebugUnitTest` | DTO/仓储等单元测试通过 |
| Android | `./gradlew assembleDebug` | APK 可构建 |
| 真机 | `scripts/adb-smoke.ps1` | App 可安装、启动、主要 UI 标记存在 |

### 8.2 人工验收

| 场景 | 验收口径 |
| --- | --- |
| 第一次打开 | 能理解这是跨平台阅读平台,不是一堆仓库 |
| 读一本书 | 能从书架或书城进入阅读,返回逻辑符合预期 |
| 读到不懂 | 能打开 AI 问书,回答不是单纯倾倒 RAG 文本 |
| 留下想法 | 划线、笔记、段评有清楚入口和关闭方式 |
| 接手开发 | 能从 PRD、TODO、Runbook 找到下一步 |

## 10. 风险与未决策

| 风险 | 影响 | 当前处理 |
| --- | --- | --- |
| 后端未验 JWT | 用户数据可越权 | ADR-001 已提出,待实施 |
| App UI 变化太快 | 老坑重复出现 | 项目记忆库 + adb 自动化逐步兜底 |
| RAG 内存索引 | 重启丢、多实例不可用 | 先接受 MVP,后续做持久化索引 |
| 需求过多 | 项目变成不可交付杂货铺 | 所有想法先进 v2/v3,按小 MVP 切 |
| 文档过多 | 读者迷路 | 本 PRD 作为第一入口,其他文档作为证据 |

## 11. 下一步

**结论**:下一步只做两件最能提高可信度的事。

1. **App 自动化点击链路**:书架搜索 → 打开阅读 → 长按段落 → 划线 → 点击划线 → 关闭/删除 → 返回书架。
2. **ADR-001 统一鉴权落地**:三服务验 JWT,删除客户端传 `userId` 的信任模型,补越权负向测试。

这两件做完,BookRealm 才能从“功能很多的 alpha”走向“主链路可信的 alpha 后期”。
